# ADR 0017: Revenue/channel analytics report — one row per order, device dimension dropped

## Status

Accepted.

## Context

Last of the five analytics/reporting-gap roadmap items. `ROADMAP.md`'s wording: "revenue broken
down by new vs. returning customer, coupon, campaign, country/city, device — none of this is
surfaced today."

Investigation found the existing revenue data is narrower than it looks:

- `Model\CampaignOutcomeLogger::getStats()` sums `sales_order.base_grand_total` only for orders
  matched as a campaign's conversion (`markActed()`'s first-plausible-match heuristic) — organic
  revenue is invisible to it, by design, not a bug. `Block\Adminhtml\Campaign\FunnelViewModel`
  (the per-campaign funnel widget) is built on the same logger and has the same scope; neither is
  a substitute for a store-wide report.
- `sales_order.coupon_code` exists and is populated by core checkout whenever a cart has an
  applied coupon — a flat column, no join needed. But `Model\CouponGenerator` marks an
  Ordo-generated code (`type = COUPON_TYPE_SPECIFIC_AUTOGENERATED`, `is_primary` null) exactly the
  same way core's own "Manage Coupon Codes" mass-generator marks a merchant-created one — nothing
  in this schema ties a code back to the campaign that minted it. "Which coupon was used" is real
  and cheap; "was this coupon Ordo's doing" is not reliably answerable today.
- `sales_order` itself has no geography columns. `sales_order_address` does
  (`country_id`, `city`, keyed by `parent_id` + `address_type = 'billing'`) — real, already
  populated by core on every order, just never joined to by anything in this module before now.
- No "new vs. returning" classification exists anywhere. `RfmCalculator::getFrequency()` gives a
  point-in-time total order count per customer, not a per-order "was this their Nth order" flag
  usable across a report's full order history.
- **Device has no real data source.** Confirmed by grep across the whole codebase and
  `ordo_visitor_event`'s schema (`entity_id, visitor_id, customer_id, event_type, event_key,
  created_at` — no user-agent, no device class) that nothing here, and nothing in a stock Magento
  install, tracks order-level device/browser. Even if it did, `ordo_visitor_event` has no join
  path to `sales_order` (no `visitor_id` column there) — the same structural gap ADR 0015 already
  ruled out for the product-performance funnel blocks this dimension too, for the same reason.

## Decision

1. **One row per order**, not per day/campaign/coupon. Coupon code, billing country/city, and
   new-vs-returning are all order-level facts with no fan-out risk; campaign attribution is a
   left join that's null for the (common, expected) case of organic revenue. A flat per-order grid
   lets the admin filter/sort by any dimension from the grid's own column filters, rather than
   this report pre-deciding one grouping axis the way a classic cross-tab would.
2. **Device is dropped entirely, not faked.** Same reasoning as ADR 0015's "not a per-visitor
   funnel, the data model can't support it honestly" — shipping a speculative or always-empty
   device column would be worse than admitting the gap. A real device breakdown needs new
   tracking (capturing `HTTP_USER_AGENT` somewhere joinable to an order) as separate, future work.
3. **Coupon code is shown as-used, not attributed.** The grid surfaces `coupon_code` as a plain
   column; it makes no claim about whether an Ordo campaign generated it. Tying a code back to its
   originating campaign would need new tracking at `Model\Campaign\Action\GenerateCoupon::execute()`
   time (e.g. a `code → campaign_id` log) — out of scope here, flagged as a known limitation.
4. **New vs. returning is computed live**, not materialized: a derived subselect
   (`MIN(entity_id)` per `customer_id` over non-canceled `sales_order` rows) joined back to the
   main order row, same "wrap a GROUP BY select as a derived table and `joinLeft` it" technique
   `ProductPerformance`'s own purchase-count subselect already uses. Guest orders
   (`customer_id IS NULL`) have no identity to compare repeats against and are bucketed as "new" —
   the simplest honest reading, not a claim that email-matching would make them a real returning
   customer.
5. **Campaign attribution needed its own dedupe.** `CampaignOutcomeLogger::markActed()`'s own
   docblock says it can credit "the most recent un-acted outcome row(s) ... across any campaign"
   to one order — `ordo_campaign_outcome_log.order_id` is not unique. A naive join would fan one
   order into several report rows and double-count its revenue. The collection pre-aggregates to
   one campaign per order (`MIN(campaign_id)`, a stable if arbitrary tie-break) before joining, so
   `main_table` stays one row per order — same "good enough for directional stats, not exact
   attribution" spirit `markActed()` itself already uses.
6. **Pattern: `ProductPerformance`-style live join over `sales_order`, not `RFM`-style
   live-aggregate-with-window-functions.** Nothing here needs cross-customer ranking the way RFM's
   quintiles do — just grouping/filtering, which the admin grid's own column filters/sort already
   give for free once each dimension is a plain column on the row.

## Consequences

- Organic (non-campaign) revenue is now visible for the first time in this module — previously
  only campaign-attributed revenue had any reporting surface at all.
- Two known, documented gaps carried forward rather than silently worked around: Ordo-attributed
  coupon revenue, and any device/channel breakdown. Both are real follow-on roadmap items, not bugs
  in this report.
- No schema change, no new cron — this is a pure read-time report, like `ProductPerformance`'s own
  purchase-count half (unlike its view-count half, which needed materialization because of
  `ordo_visitor_event`'s retention pruning — `sales_order`/`sales_order_address` are never pruned).
